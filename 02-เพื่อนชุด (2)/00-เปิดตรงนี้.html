4. ไล่หนึ่ง Request ตั้งแต่เข้าไปจนตอบกลับ

ตัวอย่าง GET /api/demo001/products/7:

Terminal
Client → express.json → /api/demo001 → GET /products/:id
       → controller อ่าน req.params.id เป็น "7"
       → numericId ตรวจและแปลงเป็น 7
       → service.getProduct(7)
       → repo.findProduct(7) → SQL + MySQL
       ← entity หรือ null
       → service ตรวจพบ/ไม่พบ → detail(entity)
       ← DTO → controller → success(res, DTO) → HTTP 200 + JSON

ถ้า repository คืน null: service โยน AppError 404 → Express 5 ส่ง rejected Promise เข้า error handler → HTTP 404 + error envelope ไม่เรียก mapper ด้วย null

จำหน้าที่จากโค้ด:

JavaScript
// Controller: จัดการ HTTP
const dto = await service.getProduct(numericId(req.params.id));
return success(res, dto);

// Repository: ดึงแถว; ไม่ใช้ res/req
findProduct: id => one(PRODUCT_SELECT + ' WHERE p.id=?', [id])

// Mapper: สร้างข้อมูลออก; ไม่ query DB
price: Number(entity.price)

await จำเป็นเพราะ service/repository คืน Promise ถ้าลืมอาจส่งข้อมูลที่ยังไม่เสร็จ แทนผล query

5. แปลงสเปกเป็นรายการแก้โค้ด

จดก่อนลงมือ ใช้ Contract Sheet ได้:

Terminal
Method/path:
Path params และชนิด:
Query + default/max:
Body: field / type / required / nullable / default
Table / PK / FK / UNIQUE:
Success: HTTP status / DTO / envelope
Errors: condition → status / code / message

ตัวอย่างวิธีคิด: สเปกบอกว่า response ต้องมี brandName

1. หาว่าข้อมูลอยู่ตารางใด: ในโครงนี้คือ brands.name

2. Repository JOIN brands แล้ว alias brand_name

3. Mapper อ่าน entity.brand_name แล้วส่ง key brandName

4. Controller ใช้ detail DTO ไม่ใช่ summary ซึ่งไม่มี field นี้

5. ตรวจ JSON จริงว่ามีค่าและชนิดถูก อย่าตรวจแค่ HTTP 200

หากสเปกเปลี่ยนจาก products เป็น resource อื่น ให้จด mapping ของทุกชื่อก่อน rename เพื่อไม่ให้ SQL เปลี่ยนแล้ว service/mapper ยังอ้างชื่อเดิม

6. ลำดับแก้ที่แนะนำ

1. ตั้ง DB/identity และเปิด schema อาจารย์

2. แก้ repository ให้ SELECT ตาราง/คอลัมน์และ key ถูกก่อน

3. แก้ validation และ business rules ใน service

4. แก้ mapper และ response envelope

5. แก้ controller/route ให้ method/path/input/status ตรง

6. แก้ pagination และ error contract

7. ทดสอบ happy path → negative cases → persistence

ค้น ADAPT ใน editor เพื่อเห็นจุดปรับ แต่ไม่ใช้ search/replace เปลี่ยนทุกคำโดยไม่อ่าน เช่น field ของ DB อาจเป็น snake_case แต่ API ต้องเป็น camelCase

7. วิธีปรับ CRUD ทั้ง 6 รูปแบบ

7.1 Create — เพิ่มข้อมูล

เปิด [controller Create](src/controllers-$id/01-create-product.js), createProduct/productInput ใน service และ createProduct ใน repository

Terminal
req.body → ตรวจชนิด/required → allowlist
         → เช็ก unique → INSERT → อ่านแถวใหม่ → detail DTO → 201

ในโครงนี้ body ขั้นต่ำคือ:

JSON
{
  "sku": "MANUAL-001", "name": "Manual Phone", "brand_id": 1,
  "category": "PHONE", "price": 1200.5,
  "ram_gb": 8, "storage_gb": 128, "color": "Black"
}

stock_quantity ไม่ส่งจะใช้ 0, status ใช้ AVAILABLE, release_date ใช้ null ตามกฎของโครงนี้ ไม่ใช่ default ของทุกข้อสอบ

แก้ productInput ให้คืน object เฉพาะ field ที่อนุญาต ไม่ส่ง req.body ทั้งก้อนลง SQL

INSERT ... SET ? ในชุดนี้ใช้ **mysql2.query** กับ object ที่ผ่าน allowlist แล้ว ถ้าเปลี่ยนเป็น execute ให้ใช้ (columns) VALUES (?,...) และ array ของค่าแทน

auto increment ใช้ result.insertId; string PK อ่านกลับด้วย key ที่ส่งมา ไม่ใช้ SELECT MAX(id)

precheck unique ช่วยให้ error ชัด แต่ยังต้องจับ ER_DUP_ENTRY เมื่อมี request ชนกัน

ถ้าโจทย์เพิ่ม filter ให้ส่ง filter ไปทั้ง list และ count ดูส่วน 9 อย่าคิดว่าโครงเดิมรองรับ search/filter แล้วโดยไม่แก้ SQL

7.4 Read 3 — รายตัว

เปิด [controller detail](src/controllers-$id/04-read-product-detail.js) → service.getProduct → repo.findProduct → detail

PUT ของโครงนี้รับ full body เหมือน POST หากส่งแค่ name จะไม่ผ่าน validation เมื่อสเปกต้องการ partial update ต้องปรับ validation/การรวมค่า/SQL ด้วย

unique check ต้องอนุญาตค่าเดิมของแถวตัวเอง: other && other.id !== id จึงถือว่าชนกับแถวอื่น ไม่ใช้ changedRows=0 ตัดสินว่าไม่พบ เพราะส่งค่าเดิมอาจยังสำเร็จ

7.6 Delete — ลบข้อมูล

เปิด [controller Delete](src/controllers-$id/06-delete-product.js) → service.removeProduct → repo.removeProduct

ตรวจ existing/affectedRows ตามโครง ถ้าลบสำเร็จตอบ res.status(204).end() ไม่มี JSON; ถ้าโจทย์กำหนด 200 ให้แก้ตาม body ที่ระบุ ไม่ใช้ success helper กับ 204

หากถูก FK อ้างอิง โครงตอบ 409 RESOURCE_IN_USE ไม่ลบตารางลูกหรือปิด FK เองโดยไม่มีข้อกำหนด Composite key ต้องมีทุกส่วนใน WHERE ไม่เช่นนั้นอาจลบหลายคู่พร้อมกัน

โครงแยก summary สำหรับ list และ detail สำหรับรายตัว/Create/Update:

| DB entity | Response | เหตุผล |

| --- | --- | --- |

| brand_id | brandId | เปลี่ยนชื่อ |

9. Pagination: แก้อะไรบ้างเมื่อสเปกต่างจากโครง

โครงปัจจุบันใช้ page เริ่ม 1, limit เริ่ม 10, cap limit ที่ 100, invalid query → 400, หน้าที่เกินท้าย → 200 + [] และ total จริง

JavaScript
const offset = (page - 1) * limit;
const totalPages = Math.ceil(total / limit);

ตัวอย่าง total=23, page=3, limit=10: offset=20, data มีได้ไม่เกิน 3 รายการ, totalPages=3, hasNextPage=false หน้า 4 data=[] แต่ total ยังเป็น 23; ถ้า total=0 totalPages=0

ต้องปรับพร้อมกันสามจุด:

1. pagination middleware: ชื่อ query/default/max/reject หรือ cap

2. repository: LIMIT/OFFSET และ ORDER BY ที่แน่นอน

3. api-response.metadata: ชื่อ key/สูตร/boolean ตาม contract

ถ้ามี ?name=... ต้องเพิ่ม validation และ filter ใน service/repository **ทั้ง SELECT และ COUNT** โดย bind ค่าผ่าน ? เหมือนกัน COUNT ไม่ใช่ rows.length เพราะ rows คือเฉพาะหน้าปัจจุบัน หากมี JOIN แบบหนึ่งต่อหลายให้นับ resource ที่ต้องการจริง ไม่ปล่อยให้แถวที่ซ้ำจาก JOIN ทำให้ total เกิน

ค่าจาก query เป็น string และ query ซ้ำอาจเป็น array โครงจึงตรวจชนิดก่อนแปลง ไม่ใช้ parseInt('2abc') ซึ่งกลายเป็น 2

10. Exception Handling: โยนตรงไหน จับตรงไหน

AppError ใน repo นี้ใช้ลำดับ **message, status, code**:

JavaScript
throw new AppError('Product not found', 404, 'PRODUCT_NOT_FOUND');

อย่าสลับกับ HttpError(status,message,code) ของ Students project เพราะจะได้ค่า status ผิด

Terminal
input ผิด → service / middleware → AppError 400
ไม่พบ → service → AppError 404
unique ชน → precheck หรือ DB → 409
DB error ไม่คาดหมาย → 500
                       ↓
             errorHandler หลัง routes → JSON error

| MySQL code | HTTP ของโครง | ความหมาย |

| --- | --- | --- |

| ER_DUP_ENTRY (1062) | 409 | PK/UNIQUE ซ้ำ |

| ER_NO_REFERENCED_ROW_2 (1452) | 400 | FK ปลายทางไม่มี |

| ER_ROW_IS_REFERENCED_2 (1451) | 409 | ยังถูกแถวอื่นอ้างอิง |

Express 5 ส่ง Promise rejection จาก async handler ไป error middleware ได้ หากย้ายไป Express 4 ต้องมี async wrapper หรือ try/catch + next(err) และลงทะเบียน handler สี่พารามิเตอร์ (err,req,res,next) หลัง routes

ไม่ catch แล้ว return undefined จน request ค้าง และไม่แปลง DB error ทุกชนิดเป็น 409 รายละเอียด SQL/stack/password ไม่ใช่ข้อความตอบ client

01 — HTTP, REST และ Status Codes

คู่มือสรุปที่ผู้ช่วยเรียบเรียงเพิ่มสำหรับอ่านประกอบโจทย์ ไม่ใช่ใบงานหรือข้อสอบใหม่ของอาจารย์

อ่าน request ให้ได้ก่อนเขียน route

HTTP request มี method, URL/path/query, headers และ body เช่น:

ตัวอย่างโค้ด
POST /api/demo001/products
Content-Type: application/json

{"sku":"MY-001","name":"Phone","brand_id":1,"category":"PHONE","price":100}

method บอกการทำงาน path ระบุ resource headers บอกชนิดข้อมูล และ body คือข้อมูลที่ส่งเข้า server Response มี status, headers และ body ตาม contract

| Method | งานที่พบบ่อย | ตัวอย่าง |

| --- | --- | --- |

| GET | อ่านโดยไม่แก้ resource | /products, /products/1 |

| POST | สร้าง resource | /products |

| PUT | แทนค่าข้อมูล resource ตาม contract | /products/1 |

| PATCH | แก้บางฟิลด์ เมื่อโจทย์กำหนดให้ใช้ | /products/1 |

| DELETE | ลบ resource | /products/1 |

PUT แบบ full body ในชุดฝึกเป็นนโยบายของตัวอย่าง อย่าเดาว่าทุกข้อสอบใช้เหมือนกัน GET ไม่ควรทำให้ข้อมูล resource เปลี่ยน PUT/DELETE โดยหลักควรมีผลสุดท้ายเหมือนเดิมเมื่อส่งซ้ำ แต่ status ของครั้งหลังอาจต่าง เช่น DELETEซ้ำ404

params, query และ body

/products/12 → req.params.id เป็น string '12'

/products?page=2&limit=10 → req.query ใช้ควบคุมรายการ ต้อง validate ก่อนคำนวณ

POST/PUT JSON → req.body หลังผ่าน express.json()

base path ของนักศึกษาเป็นค่าคงที่ เช่น /api/demo001 ไม่ใช้ /api/:studentId ส่วน product ID ใช้ route param ได้

Status ที่ต้องเลือกถูก

| Status | ความหมาย/ใช้ในโจทย์ |

| --- | --- |

| 200 | สำเร็จ มี JSONตามสเปก |

| 201 | สร้างสำเร็จ |

| 204 | สำเร็จและไม่มี response body |

| 400 | request/validationไม่ถูกต้อง |

| 404 | route หรือ resourceไม่พบ |

| 409 | ข้อมูลชนกัน เช่น UNIQUE หรือ resourceยังถูกอ้างอิง |

| 500 | server errorที่ไม่คาดคิด |

statusในบรรทัด HTTP กับข้อความใน JSON เป็นคนละอย่าง res.json({status:404}) อย่างเดียวไม่ได้ทำให้ HTTP เป็น404 ต้อง res.status(404).json(...)

ลองอธิบายก่อนสอบ

ทำไม GET detailไม่พบต้อง404แต่ GET listไม่มีรายการยัง200พร้อม[]? ทำไม POSTสำเร็จ201? ทำไม204ห้ามแนบJSON? ทำไม priceในbodyต้องตรวจชนิด แม้ clientเขียนมาว่าเป็นnumber?

02 — Express และ JavaScript ESM

โครงที่ต้องมี

JavaScript
import express from 'express';
const app = express();
app.use(express.json());
app.get('/api/demo001/ping', (req, res) => {

});
app.listen(3000, '127.0.0.1');

Middleware และ Router

ลำดับมีผล: express.json → router → not-found middleware → error middleware ถ้า body parserอยู่หลัง route จะอ่านJSONไม่ได้ ถ้า error handlerอยู่ก่อนroute อาจไม่รับ errorจากrouteที่อยู่ถัดไป

JavaScript
const router = express.Router();
router.get('/products/:id', async (req, res) => {
  const dto = await service.getProduct(req.params.id);
  return res.json({success:true,data:dto});
});
app.use('/api/demo001', router);

snippetนี้แสดงการใช้ Router เท่านั้น ต้องมี service ที่ประกอบแล้วและตรวจidก่อนเรียกตามเฉลยจริง

async/await กับ DB

DB query คืน Promise ต้อง await ก่อนใช้ผลลัพธ์ mysql2/promise คืน [rows, fields] สำหรับSELECT และ [result, fields] สำหรับ INSERT/UPDATE/DELETE

JavaScript
const [rows] = await db.query('SELECT id,name FROM products WHERE id=?', [id]);
const entity = rows[0] ?? null;

Express5ที่ kitใช้ส่ง rejected Promiseจาก async handlerเข้าสู่ error middlewareได้ หากใช้ Express4 ต้องส่ง next(err) ผ่าน try/catchหรือwrapperตามโครงงาน

app กับ server ต่างกัน

[app.js](../src/app.js) ประกอบ routes และ export factory แต่ยังไม่เปิดport ส่วน [server.js](../src/server.js) อ่าน config สร้าง pool ตรวจฐานฝึกและ listen การ node app.js อย่างเดียวจึงไม่เปิดAPIของkit

function positiveInteger(value, fallback) {
  if (value === undefined) return fallback;
  if (typeof value !== 'string' || !/^\d+$/.test(value)) throw new AppError('page and limit must be positive integers');

export function parsePagination(query = {}) {
  const page = positiveInteger(query.page, 1);
  const limit = Math.min(positiveInteger(query.limit, 10), 100);
  const offset = (page - 1) * limit;
  if (!Number.isSafeInteger(offset)) throw new AppError('Requested page is too large');

วิธีด้านล่างแยกสองทาง: ถ้ามี Import/Collections ใช้ส่วน 3; ถ้าใช้ lightweight หรือไม่มี variables ให้ใช้ URL เต็มและสร้าง request ตามส่วน 4 ไม่ต้องลงชื่อเข้าใช้เพื่อทำตามวิธี URL เต็ม

4.7 D1 — DELETE และตรวจหลังลบ

Method DELETE, URL ลงท้าย ID ที่คุณสร้าง คาดหวัง **204 และ Body ว่าง** หลังจากนั้นเปลี่ยนเป็น GET URL เดิมแล้ว Send ควรได้ 404

ไม่เลือก brand id หรือ product id อื่นที่ไม่ได้ตั้งใจลบ ถ้าแถวยังมี FK อ้างอิงอาจได้ 409 ตาม contract

5. อ่านผลให้ครบ ไม่ดูแค่สีเขียว

Status คือ HTTP status จริงจาก Postman ไม่ใช่เลขที่เขียนไว้ใน JSON

Body: ตรวจชื่อ key/ชนิด/array vs object/DTO/pagination

Headers: JSON ควรมี Content-Type ที่ตรง

เปลี่ยนข้อมูลแล้ว GET อีกครั้ง และตรวจแถวใน DB ด้วย key เพื่อยืนยัน persistence

Response 204 ต้องไม่มี Body; response 404/409 ต้องตรง error envelope ที่โจทย์กำหนด

ลองส่ง page=0, ID ที่ไม่มี, ขาด required field และ SKU ซ้ำ เพื่อยืนยัน 400/404/409 ของโครงนี้ ก่อนแก้ตามสเปกจริง

guides/02-crud.md

CRUD ทีละชั้น

เปิดไฟล์ตามเส้นทางนี้: src/app.js → routes-$id/catalog-route.js → services-$id/catalog-service.js → repositories-$id/catalog-repository.js → mappers-$id/product-mapper.js

Route และ async

app.js รับ db pool แล้วประกอบ service/repository ติด router ที่ /api/${studentId} โดย studentId เป็นค่าจาก config ตอนเริ่มโปรแกรม express.json() ต้องอยู่ก่อน router และ error handler อยู่ท้ายสุด

Express 5 ส่ง rejected Promise ของ async handler ไป error middleware ได้ Express 4 ต้องใช้ try/catch + next(err) หรือ wrapper; ตรวจเวอร์ชันก่อนคัดลอก

1C: Create

route รับ req.body → service ตรวจ/allowlist input → ตรวจ SKU ซ้ำ → repository INSERT → ใช้ result.insertId เฉพาะ auto increment numeric key → SELECT ใหม่ด้วย JOIN → detail DTO → 201

DB UNIQUE ยังจำเป็นแม้เช็กก่อน INSERT เพราะ request พร้อมกันอาจผ่าน precheck ทั้งคู่ ห้ามใช้ SELECT MAX(id) หาว่าตนสร้างแถวไหน

3R: Read

รายการ brands: SELECT list ตามลำดับแน่นอน

รายการ products: query parser → LIMIT/OFFSET และ COUNT → summary DTO + metadata

รายละเอียด: find by key พร้อม JOIN → ถ้าไม่พบ throw 404 ก่อนเข้า mapper

โจทย์จริงอาจจัด 3R ต่างกัน ให้ดู endpoint ของข้อสอบ ไม่มีหลักประกันว่าจะใช้ชื่อ resource เหมือน kit

1U: Update

ตรวจว่ามีแถวก่อน → validate full body → ถ้า SKU ของอีก id ซ้ำตอบ 409 → UPDATE ด้วย WHERE id=? → อ่านแถวกลับ ตอบ 200

การส่งค่าเดิมทุกฟิลด์เป็น update ที่ถูกต้อง อย่าใช้ changedRows===0 ตัดสินว่าไม่มีแถว เพราะอาจมีแถวแต่ค่าไม่เปลี่ยน

1D: Delete

ตรวจแถว → DELETE WHERE id=? → ตรวจ affectedRows → 204 .end() โดยไม่ส่ง JSON ถ้าสเปกเป็น W6 ให้ส่ง 200 พร้อม envelope ตามโจทย์ หาก FK อ้างอิงอยู่ให้ปล่อย error เข้าตัวแปลงกลาง

SQL ที่ต้องเขียนเองได้

SQL
SELECT id, sku, name FROM products ORDER BY id LIMIT ? OFFSET ?;
SELECT COUNT(*) AS total FROM products;
SELECT p.id, p.name, b.name AS brand_name
FROM products p JOIN brands b ON b.id=p.brand_id WHERE p.id=?;
INSERT INTO products (sku,name,brand_id,category,price) VALUES (?,?,?,?,?);
UPDATE products SET name=?, price=? WHERE id=?;
DELETE FROM products WHERE id=?;

ส่ง values ผ่าน parameter binding ไม่ต่อ string จาก request ลง SQL ตัวอย่าง repo ใช้ query('INSERT ... SET ?', [data]) กับ object ที่ service เลือกฟิลด์ไว้แล้ว ซึ่ง mysql2 .query รองรับ อย่าสลับเป็น .execute แล้วส่ง object แบบเดียวกัน

ทดสอบด้วยข้อมูลของตัวเอง ดู SQL persistence หลัง POST/PUT และ GET หลัง DELETE ไม่ถือว่า response อย่างเดียวพิสูจน์การบันทึกแล้ว

guides/03-pagination-dto.md

Pagination, DTO และ JOIN

Pagination

kit กำหนด page เริ่ม 1, limit เริ่ม 10 สูงสุด 100 รับ string ตัวเลขจำนวนเต็มบวกเท่านั้น หากส่งผิดหรือส่งซ้ำตอบ 400 ตัวอย่าง page=1.5, page=0, page=abc, limit=0, page=1&page=2

JavaScript
const limit = Math.min(requestedLimit, 100);
const offset = (page - 1) * limit;
const totalPages = Math.ceil(total / limit);

ต้องคำนวณ offset หลัง cap limit ใช้ ORDER BY ที่แน่นอน และ COUNT ใช้ filter เดียวกับรายการ กรณีไม่มีข้อมูล total=0, data=[], totalPages=0 ห้าม fallback เป็นจำนวนอื่นด้วย || หน้าเกินสุดท้ายยัง 200 พร้อม [] และ total จริง

kit ไม่มี search/filter; ถ้าโจทย์เพิ่ม ต้องแก้ทั้ง list และ count ให้ตรงกัน นโยบายไม่ส่ง page/limit คือยังแบ่งหน้าด้วย default หากโจทย์ต้องคืนทั้งหมดเมื่อไม่มี query ใช้ recipes/optional-pagination.js แล้วแยก SQL แบบไม่มี LIMIT ให้ครบ ไม่ใช่แก้แค่ parser

DTO allowlist

summary มี 7 ฟิลด์: id, sku, name, brandId, category, price, status

detail มี 13 ฟิลด์: id, sku, name, brandId, brandName, category, price, ramGb, storageGb, color, stockQuantity, status, releaseDate

อย่าใช้ {...entity} เพราะอาจหลุด internal_cost และชื่อคอลัมน์ DB ไม่ตรง API DTO แปลง snake_case → camelCase ด้วย mapping ชัดเจน เช็ก null ก่อน mapper เพื่อให้ missing เป็น 404

mysql2 มักคืน DECIMAL เป็น string จึงใช้ Number(entity.price) ใน DTO ตาม contract นี้ DATE ใช้ dateStrings เพื่อรักษาวันเดิม releaseDate เป็น YYYY-MM-DD หรือ null; timestamp ของ envelope เป็น ISO UTC ไม่ใช่ DATE

JOIN

products มี brand_id แต่ detail ต้อง brandName จึงต้อง JOIN brands แล้ว alias b.name AS brand_name ห้ามเดาหรือ hardcode ชื่อ brand

ถ้าใช้ LEFT JOIN ต้องกำหนดว่าค่าไม่มี brand เป็น null หรือ error ตามโจทย์ ใน kit FK บังคับ brand และใช้ INNER JOIN

เพิ่มสินค้า — คำถาม เฉลย และวิธีทำ

คำถามย่อจากงานWeek08ที่templateทำไว้แล้ว ส่วนเฉลยเป็นโค้ดของโครงนี้ ไม่ใช่โจทย์ใหม่ให้ทำเพิ่ม ลำดับ6ส่วนจัดเพื่อค้นหาโค้ด ไม่ใช่การยืนยันข้อสอบกลางภาค

คำถาม

POST /products ภายใต้basepathคงที่ /api/รหัสของตัวเอง

พัฒนา API เพิ่มสินค้า รับ JSON ที่มี sku, name, brand_id, category, price, ram_gb, storage_gb, color และฟิลด์อื่นตาม schema บันทึกลง MySQL สำเร็จตอบ201 หาก SKU ซ้ำตอบ409 ส่งข้อมูลกลับตาม response contract

วิธีคิดก่อนเขียน

ต้องบันทึกจริง จึงต้องมีINSERT ไม่ใช่ส่งbodyเดิมกลับอย่างเดียว

brand_idอ้างอิงbrands; ถ้าปลายทางไม่มีต้องจัดการFKerror

skuห้ามซ้ำ ใช้precheckเพื่อข้อความอ่านง่ายและDB UNIQUEเพื่อกันการชนพร้อมกัน

ไม่ให้clientกำหนดidหรือinternal_cost จึงเลือกฟิลด์ก่อนส่งSQL

สร้างแล้วต้องอ่านกลับด้วยinsertId จึงได้ค่าที่DBกำหนดและbrandNameจากJOINสำหรับdetailDTO

วิธีทำทีละขั้น

1. อ่านbodyที่controller แล้วส่งให้service.createProduct

2. productInputตรวจ8ฟิลด์บังคับ ชนิดnumber/stringและNOT NULL ให้ตรงschema

3. findBySkuตรวจซ้ำ แล้วcreateProductในrepository INSERT objectที่ผ่านallowlistแล้ว

4. ใช้insertIdอ่านfindProductพร้อมJOIN แปลงdetailDTO

5. controllerตอบ201; duplicateหรือFKerrorส่งเข้าmiddlewareกลาง

โค้ดนี้ใช้จริงในtemplate โดยservice/repository/mapperที่ต้องใช้ร่วมกันอยู่ครบตามลิงก์ถัดไป ไม่ใช่handlerเดี่ยวที่รันได้โดยไม่มีlayerอื่น

JavaScript
// ADAPT: controller ที่ใช้ได้แล้ว เปลี่ยนparams/body/statusตามโจทย์ และแก้service/repo/mapperที่เกี่ยวข้อง
// Create: validate/allowlist → INSERT → SELECT detail DTO → 201
import {success} from '../mappers-$id/api-response.js';

export function createProductHandler(service) {
  return async function (req, res) {
    return success(res, await service.createProduct(req.body), 201);
  };
}

คำถาม
